Pipeline de Streaming End-to-End
Apache Kafka + Apache Beam — Transacciones Bancarias Sinteticas

1. Introduccion

Este documento describe el diseno e implementacion de un pipeline de streaming end-to-end que procesa eventos de transacciones bancarias sinteticas. El sistema demuestra los conceptos fundamentales del procesamiento de streams en tiempo real:

  • Procesamiento basado en tiempo de evento (no de procesamiento)
  • Ventanas fijas de 30 segundos
  • Deduplicacion por identificador de evento
  • Manejo de eventos tardios y fuera de orden
  • Salida idempotente a archivos JSON

5. Decisiones de Diseno

5.1 Tiempo de evento vs. tiempo de procesamiento

El campo event_time del payload se extrae y se asigna como timestamp de Beam via TimestampedValue. Esto garantiza que eventos tardios sean asignados a la ventana correcta de negocio, independientemente de cuando lleguen al broker. Sin esta decision, los eventos tardios se agruparian en la ventana del momento de llegada, produciendo resultados incorrectos.

5.2 Ventanas fijas de 30 segundos

FixedWindows(30) agrupa eventos en segmentos de 30 segundos. Cada segmento produce resultados independientes por cuenta. Representa el patron tipico de micro-batching en pipelines de fraude o reporting en tiempo real.

5.3 Latencia permitida (allowed_lateness = 60s)

Acepta eventos hasta 60 segundos despues del cierre de la ventana. El trigger tardio Repeatedly(AfterProcessingTime(5s)) re-dispara cada 5 segundos mientras sigan llegando eventos tardios. Modo DISCARDING: cada trigger produce solo los nuevos datos, sin acumular.

5.4 Deduplicacion por event_id

DeduplicateByEventId mantiene un set de event_id por bundle. En la ejecucion real se eliminaron 17 duplicados de 127 mensajes (13%). Para runners distribuidos como Flink o Dataflow, se reemplazaria con beam.Distinct() o la State API.

5.5 Salida idempotente

Cada archivo se nombra result_<md5(window_start + account_id)[:10]>.json. Re-ejecutar el pipeline con los mismos datos produce exactamente los mismos archivos con el mismo contenido, sin duplicacion en disco.

5.6 DirectRunner

Se uso el runner local para facilitar la demostracion sin infraestructura adicional. El codigo es compatible con Apache Flink o Google Cloud Dataflow cambiando unicamente la configuracion del runner en PipelineOptions.
